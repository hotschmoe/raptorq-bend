# GF(256) (RFC 6330 section 5.7) -- `src/gf256.bend`

Run the tests: `bend tests/gf256_test.bend` (about 10 s; prints `ALL PASS`, exits 1 via `IO.die` on failure).
Check laws: `bend src/gf256.bend` (prints `ALL PROOFS CHECK`). Regenerate tables and test checksums: `python3 tools/gen_gf256.py`.

## Octets
An octet is a `U32` < 256 (Bend has no U8). Field: x^8+x^4+x^3+x^2+1 (0x11D), alpha = 2.
`oct_exp` (510 entries) and `oct_log` (index 0 is a dummy) are literal-`match` functions
generated by `tools/gen_gf256.py` from the RFC text. The script refuses to write unless the RFC tables
equal the tables in `ref/raptorq-rs/src/octet.rs` and a field generated from the polynomial, and unless
all 65536 products equal a table-free shift-xor multiply.
`add` = XOR, `mul`, `div`, `inv` follow 5.7.2 exactly (`div` by 0 and `inv(0)` return 0; RFC leaves them undefined).
`mul_slow` is a table-free multiply used only for cross-checking.

## Symbol representation: packed words, 4 octets per U32
A symbol is a `Vec`: a balanced binary tree (`VNode{l,r}`, `VWord{w}`, `VNil`), each leaf one U32 holding
4 octets (octet 4k+j at bits 24-8j..31-8j, i.e. big-endian within the word).
Why packed rather than one U32 per octet:
* XOR (the hot operation in RaptorQ: nearly all encoder/decoder work is symbol XOR) does 4 octets per op and
  the tree has 4x fewer nodes (memory and allocation is the dominant cost in Bend's runtime).
* `dst ^= c*src` needs no table lookups at all: `mulw(c, w)` is 8 steps of SWAR "multiply by alpha"
  (`xtime4`: `((w & 0x7f7f7f7f) << 1) ^ (((w >> 7) & 0x01010101) * 0x1d)`) conditionally XORed by the bits of c.
  That is branch-free and avoids the 256-way literal matches that table lookups compile to.
  `c = 0` and `c = 1` are special-cased to a no-op and a plain XOR.
* RFC symbol sizes T are multiples of Al = 4, so no padding is needed.
Cost: converting to/from per-octet access needs shifts/masks (see `byte`/`pack4` in the tests).

Trees are zipped (`Vec.xor`, `Vec.muladd`, `Vec.scale`, `Vec.zeros`). The halves are forked (`l r = f(..) f(..)`)
only while a subtree holds more than 2^`CUT_LOG2()` = 4096 words; below that the walk is sequential (see "Fork cutoff"). Both operands must have the same shape; `Vec.from_list` is
deterministic in the list length so equal-length symbols always match (a mismatch returns the first operand's
subtree unchanged, for totality). Ops are functional (`muladd` returns the new dst).

## Tested
Exhaustive over all 256x256 pairs: mul vs carry-less mul, commutativity, table checksum (independent Python
field), div checksum, `(a/b)*b = a`, `a/b = a*inv b`, `a*inv a = 1`, log/exp round-trip, distributivity,
associativity (c derived from a,b), identity, additive self-inverse; `mulw` vs per-octet `mul` for every
(c, octet) in every byte lane; `Vec` ops vs list reference for n = 1..24 words and 8 scalars.

## Fork cutoff (measured, native binary, 12 threads)
The Bend runtime executes parallel work in bulk-synchronous rounds: each fork reached by sequential code costs one
round, ~0.3 ms with 12 threads (two condvar turns), i.e. thousands of word operations. Forking every tree node (the
old code) made multi-threaded runs 10-300x slower on small symbols (e.g. 2000 muladds of 4 words: 1 ms at
`--threads 1`, 575 ms at `--threads 12`; 1024 sequential-context muladds of 256 words: 1.2 s vs 71 s).
Now `Vec.xor/muladd/scale/zeros` compute a fork depth once (`Vec.fork_levels`, from the right spine) and only fork
vectors above 4096 words (16 KiB); RaptorQ symbols (<= 8 KiB) never fork, so these ops cost the same at any `--threads`.
Chain of N muladds on one big vector, 12 threads vs 1 (ms for 100 ops): 65536 words 139 vs 153, 262144 words 269 vs 591.
Few large forks are worse than none (4 tasks of 64k words: 2.5x slower than sequential), so the cutoff is low enough
to produce many tasks whenever it forks. Forks inside an already-parallel region run inline and cost nothing.
Row-level parallelism (many independent symbols per pass) is the useful granularity: see `docs/perf.md`.

## Known limits / performance notes
* Rough speed (Bend run on C backend, 12 cores): ~9M word-muladds/s ( ~36 MB/s of symbol data) for a 16384-word
  vector; I could not build binaries (`bend -o` fails: clang 15 has no x86_64 triple support here), so thread
  scaling was not measured. A leaf of one U32 is allocation-heavy; a leaf holding several words is a possible
  later optimisation.
* Recursion deeper than ~16k-32k non-tail frames (`words`/`List.take` on 32768-element lists) crashed with
  "memory fault (machine stack overflow?)" under `bend file.bend`; `Vec` itself is only log-depth.
