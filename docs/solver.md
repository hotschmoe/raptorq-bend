# Solver (RFC 6330 section 5.4.2) -- `src/solver.bend`

Public API (see `docs/interfaces.md`; `plan`/`apply` below): `Solver.solve(l, rows)`, `Solver.solve_p(l, p, rows)` (p = number of permanently inactive
trailing columns, `R.P(sp)` for RaptorQ), `Solver.solve_dense(l, rows)` (oracle), `Solver.inactive_count(l, p, rows)`
(diagnostics). All return `Maybe<&2, List<&2, Sym>>`: `Some(C[0..l-1])` or `None` when rank < l. `rows : List<&2, Row>` (what
`Constraints.*` produce). Added with the performance work (same answer as `solve_p`, opt-in parallelism, see `docs/perf.md`):

* `Solver.solve_par(l, p, d, rows)`: the symbols are cut into 2^d word ranges that are solved concurrently (d is capped at
  log2(words per symbol); d = 0 is `solve_p`). Worth it for symbols >= 256 octets with `--threads` >= 8 (d = 3): 1.5-3.5x faster at
  K = 1000..10000, T = 256..4096. Costs CPU x 2^d (each slice repeats the symbol-independent work).
* `Solver.solve_auto(l, p, rows) : IO(Maybe<&2, List<&2, Sym>>)`: `solve_par` with d = 0 below 64 words per symbol, else
  min(3, log2 `IO.thread_count()`).

Tests (all exit non-zero on failure):
* `bend tests/solver_test.bend` (~7 s, `ALL PASS`): 24 synthetic GF(256) systems from `tests/solver_fixtures.bend`
  (generated by `python3 tools/gen_solver_tests.py`, known solutions): dense square l = 1..60, dense overdetermined,
  rank deficient (duplicate row, too few rows, zero column), RaptorQ-shaped sparse (l = 12..150, binary LT/LDPC rows plus
  dense GF(256) HDPC-like rows, shuffled terms), sparse rank-deficient, sparse with duplicate/zero terms, and a wide-sparse system
  (l = 300, rows of 73 terms: more than the 63-weight bucket cap). `solve_dense`, `solve_p` and `solve_par` (d = 1) are checked
  against the known solution / expected `None`.
* `bend tests/solver_golden_test.bend` (~10 s, `ALL PASS`): real systems `fixed(sp,T) ++ source_rows(sp, source)`
  from `src/constraints.bend` for (K,T) = (1,2,10,26 x 16,32), (50,16), (100,16), (500,4), (1000,4); the solution must equal
  the RFC intermediate symbols of `tests/vectors/intermediate.txt` bit for bit (dense oracle too for K <= 100, `solve_par` with
  d = 3 for all).
* `bend tests/solver_bench.bend -o sb; ./sb [--threads N] -- <K> <mode> [<T octets> [<d>]]`: builds the K' system for random source
  symbols, solves it, and verifies C by re-encoding every source ISI (mode 0), or times the solve (mode 5; 6 = dense oracle,
  8 = `solve_auto`, 3 = tail size). Large cases: `./sb -- 56403 5 16` (15 s), `./sb --threads 12 -- 10000 5 1024 3`.

## Plan / apply (RFC 5.4.2.2; details and numbers in `docs/plan_apply.md`)
`Solver.plan(l, p, rows) -> Maybe<&2, Plan>` looks only at the coefficients of the rows (rhs ignored) and records pivot order,
the elimination logs and the dense-tail solution as a matrix; `Solver.apply(plan, rhs: List<Sym>) -> List<Sym>` replays it on one
rhs symbol per row (same order). `solve_p`, `solve`, `solve_par`, `solve_auto` are plan + apply (`solve_par` plans once and applies to
2^d symbol slices concurrently; `apply_par(d, plan, rhs)`, `apply_auto(plan, rhs) : IO`); `solve_dense` is untouched. Tests:
`solver_test` / `solver_golden_test` check apply(plan) against the known / RFC solutions and reuse one plan on two other payloads
(T = 4 octets, and T doubled); `codec_plan_test` does the same on the golden codec vectors.

## Symbol arena (apply)
`Solver.apply` replays the plan on one flat `Array<U32>` (all rhs / pivot / tail-row / solution symbols as slices, plus a 64K product table
for symbols of >= 8 words): see `docs/plan_apply.md` (update) and `src/flat.bend`. `Solver.apply_arena` returns the arena itself.

## Algorithm
Dense baseline (`dg_*`, unchanged, also used for phase 2): rows are packed coefficient `Vec`s (4 octets per word, like symbols) + RHS
symbol in a balanced tree. Step c: one pass over the tree eliminates column c from every row (full Gauss-Jordan) and, fused into the
same pass, reduces to the next pivot candidate (`DP{tree, Cand}`), so there is exactly one divide-and-conquer pass per column.
Rank < n is detected when no row has a nonzero entry in column c.

Inactivation decoding (default), following RFC 5.4.2 in spirit:
1. **Input**: each row is normalised (sorted by column, duplicate columns XORed, zero coefficients dropped). A row with more than
   `DENSE_MIN` (48) terms covering more than l/4 columns is a dense row `Dn` (the HDPC rows; full-width coefficient `Vec`, never a
   pivot). Every other row is sparse `Sp{id, w, act, own, log, oc, r0}`: `act` = terms in ACTIVE columns (the last `p` columns start
   inactive), `w = |act|`, `own` = the row's terms in inactive columns keyed by *inactivation position*, `log` = eliminations
   received, `oc`/`r0` = the normalised original terms and rhs (for phase 3).
2. **Phase 1** (`p1_*`): state = `Array<Rw>` of rows by id, an `Array` of current weights, an `Array` of weight buckets (row ids,
   stale entries skipped; weights >= 63 share the last bucket) and the column -> rows index `ci`. Each step pops the lightest row
   (weight >= 1), its first active column is the pivot column `pc`, its other w-1 active columns are INACTIVATED and get the next
   positions. Only the rows in `ci[pc]` and `ci[inactivated columns]` are touched (`cand_loop`): the row loses those columns from `act`
   (terms in inactivated columns move to `own`, consed on) and, if it contains `pc`, logs `(g, j)` = `g = coef/pcf`, pivot number j.
   The active part never fills in, so the index only shrinks. The pivot row (pc, coefficient, `own` + the inactivated terms, log,
   original equation) is stored in the pivot list. Stops when no sparse row has an active column. Symbols and inactive coefficients are
   not touched in this phase.
3. **Materialisation** (`mat_*`): in pivot order, `V_k = pack(own_k) + sum g * V_j`, `R_k = rhs_k + sum g * R_j` over the log entries
   (`V` = coefficients over the tail columns Ci packed 4 per word, `R` = symbol), kept in an `Array<VR>`. Leftover sparse rows
   (`act` empty) are materialised the same way. Ci = permanent columns, then inactivated columns in order of inactivation, then
   columns that stayed active but appear in no row.
4. **Dense rows** (`ds_*`): `row_d -= g_k * (V_k|R_k)` for every pivot k, `g_k = orig_d[pc_k] / pcf_k` (an earlier pivot never changes a
   dense row's coefficient at a later pivot column, because pivot rows contain no other pivot column).
5. **Phase 2**: the dense system over Ci (leftover rows + corrected dense rows), solved by the dense Gauss-Jordan above. This is where
   rank deficiency shows up.
6. **Phase 3** (`p3_*`): forward substitution in pivot order through the ORIGINAL equation of each pivot: `C[pc_k] = (rhs0_k +
   sum coef_c * C[c]) / coef_pc` where every other column c is an earlier pivot column or an inactive column (already known). Finally the
   symbols are assembled in column order.

Deviations from RFC 5.4.2: no special graph-component rule for r = 2 rows (we take the most recently pushed lightest row, always
inactivate all but the first active column of it; measured: the rule would shrink the tail by 4-10 %, see `docs/perf.md`), and no
separate phases 4/5 (the result is the same unique solution since A has full rank). Measured tail size (inactive columns incl. the P
permanent ones): K=1000: 79 (P=50), 4000: 142 (100), 10000: 218 (158), 20000: 317 (224), 56403: 604 (375).

## Benchmarks (details and diagnosis in `docs/perf.md`)
Solve only, `--threads 1`, T = 16 octets: K=100 4 ms, 500 24 ms, 1000 53 ms, 2000 0.12 s, 4000 0.28 s, 10000 0.91 s, 20000 2.7 s,
K'=56403 (L=57326) 14.7 s (before: 0.57 s at K=1000, 8.3 s at K=4000, 57 s at K=10000, hours at K'=56403). T = 1024 octets: K=1000
0.29 s, 4000 1.4 s, 10000 4.0 s, K'=56403 36 s; with `solve_par` d=3 on 12 threads 0.10 s, 0.60 s, 2.1 s, 24 s.

## Parallelism
* The solver itself is sequential (`solve_p`): its work is a chain of small steps, and every parallel region reached from sequential
  code costs ~0.3 ms in this runtime (see `docs/perf.md`), so forking per pass loses. The row-tree passes of the dense tail solve still
  take a fork depth `PAR()` (2^PAR tasks per pass, default 0) and `par_for` forks only passes with >= 32768 words of work;
  measured: no gain at the sizes that occur (tail <= 604).
* Symbol slicing (`solve_par`) is the parallelism that works: one top-level task per slice, no synchronisation inside.
* gf256's `Vec` ops no longer fork below 4096 words, so `--threads N` no longer changes sequential timings.

## Bend gotchas found
* `match` scrutinees must be matched in parameter order (`match d` before `match live` when `d` is declared first), a `let`-bound or computed
  value cannot be a scrutinee (give it its own def or pass it as a parameter) and a `let` may not precede a `match` on a parameter;
  recursive calls need the shrinking parameter FIRST (termination checker reads arguments left to right), so a fuel `Nat` goes first,
  then flags, then the data. Bool/Cmp decisions inside a recursion are passed as arguments computed by non-recursive helpers (`pick_l`,
  `pick_u`, `st_pick`, `ts_flt.step`) or as state structs (merge loops: `Mg`, `Sc`, `Wk`) because helper -> main recursion is mutual
  recursion. Nested patterns and tuple patterns on parameters work: `case Lg{+g, j} <> t Tuple{ar, x}:`; a variable bound by a
  multi-scrutinee `case` cannot be scrutinised again, a constructor pattern in the same `case` can.
* A loop that needs the result of `Array.get/swap` takes it as a parameter (the caller passes `Array.get(..)` of the next element), see `pk_scan`,
  `gather`, `mat_go`. `A & B` values are matched with `Tuple{a, b}`.
* `Array` is a linear `Type`: a state struct holding Arrays is `type P1 is Type:`; indices wrap around (a bucket index > size-1 silently
  aliases another bucket); `Array.get` needs a `Data` element type (`List<&2, U32>`, `Rw`, `VR`, `Vec` are).
* A `Nat` fuel parameter that is used inside a branch and in the recursive call needs `+d: Nat`; `Nat` fuel can be `1000000000n`.
* Operators need an annotation: `(a + b : U32)`, `(1n + x : Nat)`.
* Pattern variables used twice need `+` in the pattern (`T.Term{+c, f}`), and constructor applications used twice need
  `+r = {Ctor{...} : T}`. Params used twice need `+`.
* A single list literal of ~36k numbers overflows the checker ("machine stack overflowed"): emit chunks of <= 600
  and `List.append` them (see `tools/gen_solver_tests.py`).
* `&1` and `&2` lists do not unify: `Maybe<List<Sym>>` (= `Maybe<&1, List<&1,_>>`) cannot be built from `&2` lists.
  Use `Maybe<&2, List<&2, _>>` throughout (matches `Constraints.*`).
* `IO.args()` returns `List<String>` which is not Data (no `+args`); match it once with list patterns. A compiled binary
  takes `--threads N -- args...`; `bend file.bend -- args` also passes args. `IO.now()` (ms, `Nat`) and `IO.thread_count()` exist; bind
  with a type: `+t : Nat <- IO.now()`.
* `Bool.eq` does not exist (write `beq`); `Bool.or` does.
* Definition order matters (a def must come before its first use).
