# Solver (RFC 6330 section 5.4.2) -- `src/solver.bend`

Public API (see `docs/interfaces.md`): `Solver.solve(l, rows)`, `Solver.solve_p(l, p, rows)` (p = number of
permanently inactive trailing columns, `R.P(sp)` for RaptorQ), `Solver.solve_dense(l, rows)` (oracle),
`Solver.inactive_count(l, p, rows)` (diagnostics). All return `Maybe<&2, List<&2, Sym>>`: `Some(C[0..l-1])` or
`None` when rank < l. `rows : List<&2, Row>` (what `Constraints.*` produce).

Tests (all exit non-zero on failure):
* `bend tests/solver_test.bend` (~6 s, `ALL PASS`): 23 synthetic GF(256) systems from `tests/solver_fixtures.bend`
  (generated by `python3 tools/gen_solver_tests.py`, known solutions): dense square l = 1..60, dense overdetermined,
  rank deficient (duplicate row, too few rows, zero column), RaptorQ-shaped sparse (l = 12..150, binary LT/LDPC rows plus
  dense GF(256) HDPC-like rows, shuffled terms), sparse rank-deficient, sparse with duplicate/zero terms. Both
  `solve_p` and `solve_dense` are checked against the known solution / expected `None`.
* `bend tests/solver_golden_test.bend` (~12 s, `ALL PASS`): real systems `fixed(sp,T) ++ source_rows(sp, source)`
  from `src/constraints.bend` for (K,T) = (1,2,10,26 x 16,32), (50,16), (100,16), (500,4), (1000,4); the solution must equal
  the RFC intermediate symbols of `tests/vectors/intermediate.txt` bit for bit (dense oracle too for K <= 100).
* `bend tests/solver_bench.bend -- <K> <mode>`: builds the K' system for random source symbols (T = 16 octets), solves it
  (mode 0 inactivation, 1 dense, 2 rows only, 3 print inactive-set size, 4 solve only) and checks C by re-encoding every
  source ISI.

## Algorithm
Dense baseline (`dg_*`): rows are packed coefficient `Vec`s (4 octets per word, like symbols) + RHS symbol in a
balanced tree. Step c: one pass over the tree eliminates column c from every row (full Gauss-Jordan) and, fused into the
same pass, reduces to the next pivot candidate (`DP{tree, Cand}`), so there is exactly one divide-and-conquer pass per
column. Rank < n is detected when no row has a nonzero entry in column c.

Inactivation decoding (default), following RFC 5.4.2 in spirit:
1. **Input**: a row with more than `DENSE_TERMS` (16) terms is a dense row `Dn` (HDPC-like; packed coefficient Vec over
   all l columns, never chosen as pivot). Others are sparse `Sp{id, w, act, ina, rhs}`: `act` = sorted terms in ACTIVE
   columns, `ina` = sorted terms in INACTIVE columns, `w = |act|`. The last `p` columns start inactive.
2. **Phase 1** (`ph1`): pick the sparse row with the smallest positive active weight w (parallel min-reduce, fused
   into the elimination pass). Its first active column is the pivot column; its other w-1 active columns are
   INACTIVATED (moved from `act` to `ina` in every row). Eliminate the pivot column from every other row (sparse rows:
   sorted merge-add of the pivot row's inactive part into `ina` and one `Vec.muladd` on the RHS; dense rows: point
   updates of the coefficient Vec). Since the other columns of the pivot row are inactive, `act` never fills in. The pivot
   row (pivot col, coefficient, `ina`, rhs) is stored and removed from the tree (pruned). Stops when no sparse row has an
   active column.
3. **Phase 2**: the dense system over the non-pivot columns Ci (inactivated + never-touched columns; sorted
   complement of the pivot columns): leftover sparse rows (`act` empty) and the dense rows restricted to Ci, solved by
   the dense Gauss-Jordan above. This is where rank deficiency shows up.
4. **Phase 3**: every pivot row `c*C[pc] + sum(ina terms) = rhs` is solved from the inactive solution
   (`C[pc] = (rhs + sum coef*C[col]) / c`); the pivot rows are independent, so this is a parallel tree map reading an
   O(log n) index tree (`ST`) of the inactive values. Finally all (column, symbol) pairs are assembled into column order.

Deviations from RFC 5.4.2: no special graph-component rule for r = 2 rows (we always inactivate all but the first
active column of the min-weight row), and the pivot rows keep their (few) inactive terms instead of the RFC's
separate phases 4/5 (the result is the same unique solution since A has full rank). Measured dense tail size
(inactive columns incl. the P permanent ones): K'=10: 14 (P=10), 26: 17 (10), 101: 36 (15), 511: 102 (35), 1002: 155 (50).

## Benchmarks
Native binary (`bend tests/solver_bench.bend -o sb`, system clang first in PATH), 12-core aarch64, wall time
of the whole process (row construction is <0.03 s), `--threads 1`. Solve only, T = 16 octets:

| K (K')        | L    | inactivation | dense oracle | dense tail n |
|---------------|------|--------------|--------------|--------------|
| 10 (10)       | 27   | 0.01 s       | 0.01 s       | 14           |
| 26 (26)       | 47   | 0.01 s       | 0.01 s       | 17           |
| 100 (101)     | 128  | 0.04 s       | 0.07 s       | 36           |
| 500 (511)     | 558  | 0.16 s       | 1.2 s        | 102          |
| 1000 (1002)   | 1071 | 0.57 s       | 6.5 s        | 155          |
| 2000 (2005)   | 2099 | 2.2 s        | -            | -            |
| 4000 (4015)   | 4157 | 8.3 s        | -            | -            |

T = 1024 octets, solve only: K=100 0.09 s, K=500 0.49 s, K=1000 1.3 s, K=2000 4.1 s.
Scaling is ~O(L^1.9): phase 1 does one pass over all remaining rows per pivot (L passes). `bend file.bend` (the
interpreter/checker route) adds a fixed ~5 s of compile time to every run; use a compiled binary for timings.

Decision: the RFC-style inactivation solver is feasible in affine Bend and 5-10x faster than the dense baseline at
K'=500..1000, so it is the default. Not feasible yet: K' near 56403 (extrapolates to many hours). The next
optimization would be an index (column -> rows) so a pivot step touches only the rows that contain the pivot column
instead of scanning all rows.

## Parallelism: what was measured
* Structure: every per-step pass is a fork/join over a balanced tree (`rp_pass`, `dg_pass`, `rt_best`, `bs_map`), with
  a fork depth knob `PAR()` (2^PAR tasks) and `par_for(rows, words)` choosing the depth from the work per pass
  (only forks when a pass has enough work). Default `PAR() = 0n` => passes are sequential.
* Measured: forking did NOT give a speedup on this runtime for any size tried (K up to 4000, T up to 1024):
  `--threads 12` was 0-60 % slower than `--threads 1` (K=1000 T=16: 0.57 s -> 0.97 s; T=1024: 1.33 -> 1.82 s), and PAR=2/4
  were not better than PAR=0. (A trivial `pow2` fork-join does scale 6.5x on 12 threads, so the runtime is fine; the cost
  is in this workload: shared `+` values read by many tasks (pivot symbol/pivot row) and allocation-heavy passes.
  Copying the pivot symbol per task made it worse.) Raise `PAR()` to experiment.
* `G.Vec.xor/muladd/scale` fork at EVERY tree node down to single words; for small symbols this costs 10-30x the work with
  >1 thread (phase 2 at 12 threads took 2 s vs 0.05 s). The solver therefore uses its own sequential `sv_xor/sv_muladd/sv_scale`
  inside each row update (same results, tested). Recommendation for `gf256.bend`: stop forking below ~64 words.

## Bend gotchas found
* `match` scrutinees must be matched in parameter order (`match d` before `match live` when `d` is declared first), and a
  `let` may not precede a `match` on a parameter; recursive calls need the shrinking parameter FIRST (termination checker
  reads arguments left to right), so a fuel `Nat` goes first, then flags, then the data. Bool/Cmp decisions inside a
  recursion are passed as arguments computed by non-recursive helpers (`pick_l`, `pick_u`, `st_pick`) or as state structs
  (merge loops: `Mg`, `Sc`, `Wk`) because helper -> main recursion is mutual recursion.
* A `Nat` fuel parameter that is used inside a branch and in the recursive call needs `+d: Nat`.
* Pattern variables used twice need `+` in the pattern (`T.Term{+c, f}`), and constructor applications used twice need
  `+r = {Ctor{...} : T}`.
* A single list literal of ~36k numbers overflows the checker ("machine stack overflowed"): emit chunks of <= 600
  and `List.append` them (see `tools/gen_solver_tests.py`).
* `&1` and `&2` lists do not unify: `Maybe<List<Sym>>` (= `Maybe<&1, List<&1,_>>`) cannot be built from `&2` lists.
  Use `Maybe<&2, List<&2, _>>` throughout (matches `Constraints.*`).
* `IO.args()` returns `List<String>` which is not Data (no `+args`); match it once with list patterns. A compiled binary
  takes `--threads N -- args...`; `bend file.bend -- args` also passes args.
* `Bool.eq` does not exist (write `beq`); `Bool.or` does.
